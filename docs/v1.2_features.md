## User Feedback on Tags, Prerequisites, Summary & Simplify ✓ Done

Allow signed-in users to report incorrect content across cards and detail views.

### Tags & Prerequisites — Card
- Small "⚑ Report incorrect tags, prerequisites" text button below the tags/prerequisites chips, above the action buttons
- Always visible, subtle grey colour — low visual weight, clear intent
- Signed-in users only (guests don't see tags or prerequisites)
- Opens a feedback modal with two free-text fields:
  - **Suggested Tags** — comma-separated, optional
  - **Suggested Prerequisites** — comma-separated, optional

### Summary & Simplify — Detail View
- Small "⚑ Report incorrect summary / simplification" link below the content body, above the bottom action buttons
- Opens a feedback modal with one free-text field:
  - **What's incorrect?** — describe the issue

### Text Field Guardrails (all feedback types)
- **Min length:** 10 characters — prevents empty / junk submissions
- **Max length:** 500 characters — shown as a character counter below the field
- **Rate limit (per minute):** 2 submissions per user per minute — enforced server-side via Redis (key: `feedback:{user_id}:minute:{minute}`, TTL 60s). Limit defined as `FEEDBACK_RATE_LIMIT_PER_MINUTE` in `constants.py` (default: 2).
- **Rate limit (per day):** 5 submissions per user per day — enforced server-side via Redis (key: `feedback:{user_id}:{date}`). Limit defined as `FEEDBACK_RATE_LIMIT_PER_DAY` in `constants.py` (default: 5).
- Submissions exceeding either limit return a 429 with a user-facing message: "You've reached the feedback limit for today. Try again tomorrow."

### API
- `POST /api/v1/feedback` — authenticated, rate limited
- Validates min/max length server-side (not just client-side)

### Schema
```
feedback (
  id               UUID PK,
  blog_id          UUID FK → blog,
  user_id          UUID FK → user,
  type             TEXT,       -- enum: 'tag', 'prerequisite', 'summary', 'simplify'
  content          TEXT,       -- free-text from user (what's incorrect / suggestions)
  created_at       TIMESTAMP,
  UNIQUE (user_id, blog_id, type)   -- one feedback per user per blog per type
)
```

### Insertion rules
- A row is only inserted if `content` is non-empty after stripping whitespace
- Card feedback modal has two fields (Suggested Tags + Suggested Prerequisites) — on submit, up to two separate requests are sent, one per type, skipping any field that is empty

### Review process
- Manual — reviewed periodically by admin
- No auto-apply — admin decides whether to retag or regenerate

- Card feedback: `mockups/signedin_feed.html`
- Summary feedback: `mockups/summary.html`

## Summary & Simplify — Separate Pages

Summary and simplify are currently views inside `index.html` toggled via Alpine.js `currentView`. Their layout differs from the feed — detail pages, not a list. Reloading on `/summary/{id}` or `/simplify/{id}` also returns a 404.

**Decision:** Move summary and simplify to separate HTML pages.

### Changes
- `templates/summary.html` — standalone summary detail page
- `templates/simplify.html` — standalone simplify detail page
- FastAPI routes: `GET /summary/{blog_id}` → `FileResponse("templates/summary.html")`, `GET /simplify/{blog_id}` → `FileResponse("templates/simplify.html")`
- Remove summary/simplify view logic from `index.html`
- Each page has its own Alpine.js component — no shared state with the feed

### Benefits
- Deep link reload works naturally — FastAPI serves the right HTML file directly
- No `currentView` toggling or shared state between views
- Cleaner, self-contained layouts per page

## Branching Strategy + Auto-Deployment via GitHub Actions ✓ Done

### Branches
- `production` — stable branch. Only merged from `develop`. Auto-deploys to DO on merge.
- `develop` — integration branch. Feature branches are merged here first.
- `feature/*` — short-lived feature branches. Pushed from local, PR'd into `develop`.

### Flow
```
local feature branch → PR → develop → PR → production → auto-deploy to DO
```

### Auto-Deployment
- GitHub Actions workflow triggers on push to `production`
- SSHs into the DO droplet
- Runs `git pull && docker compose up -d --build`
- Runs `docker compose exec app alembic upgrade head` after containers are up
- GitHub secrets needed: `DO_HOST`, `DO_SSH_KEY`

### Release Notes
- Runs as a step in the same workflow, after successful deployment
- Auto-generates a GitHub Release from PR titles/descriptions merged since the last release
- GitHub secrets needed: `GITHUB_TOKEN` (available by default)
